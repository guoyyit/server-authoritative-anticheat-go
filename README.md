# 服务端权威的对局行为校验与作弊判定

本仓库实现了一套服务端权威的对局行为校验与作弊判定能力。客户端上报的角色操作
与状态变更通过**本地回环（TCP loopback）或内存管道**送达，服务端据此判定对局
过程中是否存在作弊。整条链路只在本进程内运行，不依赖任何外部服务，判定结论
可以在本地复现与验证。

## 架构总览

```
客户端 ──内存管道/回环──> Server ──> MatchEngine（单局单 goroutine）
                                         │
                                         ├─ 序号排序（去重 / 迟到 / 回退 / 跳跃）
                                         ├─ 规则评估（版本化规则集）
                                         ├─ 状态应用（服务端权威）
                                         └─ 判定记录（有界、可追溯）
```

- **传输层**（`internal/transport`）：`MemoryPipe` 内存管道、`JitterPipe` 确定性
  抖动管道、`LoopbackServer/Client` TCP 回环。
- **引擎**（`internal/engine`）：每个对局一个 goroutine，所有状态变更在持锁状态下
  串行完成，保证任意时刻读到的状态与判定是自洽的单个已提交版本。
- **规则**（`internal/rules`）：版本化规则集，内置时间、速度、传送、攻击频率、
  资源、伤害六条规则。
- **重放**（`internal/replay`）：记录操作流（含服务器接收时间与边界拒绝原因），
  按绑定的规则版本逐条件重放。
- **复核**（`internal/review`）：在状态副本上重估，不改写原始判定。
- **安全**（`internal/security`）：HMAC-SHA256 操作签名，识别篡改与伪造。

## 判定语义

### 序号与顺序（需求 1）

每个玩家的操作携带单调递增的序号（`Seq`）。引擎维护：

- `AppliedSeq`：已应用的最高序号（前沿）。
- `AppliedSeqs`：最近已应用序号的有界去重窗口。
- `Pending`：乱序到达的在途操作（按序号排序后补全）。

应用规则：

- 序号**严格按序**应用：只有 `AppliedSeq+1` 被应用，乱序到达的操作进入等待队列，
  待前驱到达后一并补全。最终应用结果与按序号顺序单次处理完全一致。
- **重复操作**（同一玩家同一序号）：在去重窗口内 → `duplicate`，绝不应用第二次。
- **迟到操作**（序号已低于前沿）：
  - 仍在去重窗口内 → `duplicate`；
  - 已超出去重窗口 → `rollback`（序号回退），绝不改写已发布的权威状态。
- **序号跳跃**（缺口超过 `MaxSeqGap`）→ `seq_jump`。
- **等待队列满**（在途操作超过 `MaxPendingPerPlayer`）→ `queue_full`。

### 规则与容差（需求 2）

所有指标与允许范围比较，超出可配置容差的被识别。容差的设计目标是**区分正常网络
抖动与真实作弊**，一次延迟尖峰不会导致误判。

| 规则 | 观测指标 | 容差与口径 |
|------|----------|------------|
| `time_skew` | 客户端时间 vs 服务器时间 | 时钟偏移 ≤ `TimeSkewAllowanceMS`；不允许未来时间（`FutureAllowanceMS`）；时间必须单调；客户端/服务器时间散度仅在服务器间隔 ≥ `DivergenceMinServerMS` 时评估（突发到达的亚秒级间隔无意义） |
| `speed` | 移动速度（距离/客户端 dt） | 速度 ≤ `MaxSpeed×(1+SpeedTolerance)` 为抖动带，无判定；超出后按比例分级，连续违规升级 |
| `teleport` | 单次位移 | > `MaxTeleportDistance` 直接判定（关键级） |
| `attack_rate` | 攻击频率 | 令牌桶：持续速率 ≤ `MaxAttackRate`，突发容量 `AttackBurst` 吸收抖动；持续超频才判定 |
| `resource` | 资源是否足以支付攻击 | 资源不足 → 严重级 |
| `damage` | 伤害值 | 超过 `MaxDamage` → 严重级；超过目标剩余血量（over-kill）→ 次要级 |

**一次超速尖峰**：速度刚超出抖动带时仅产生 `warning`（边界，标记但不拒绝），
连续违规才升级到 `minor`（可拒绝）。这样既不漏判真实作弊，也不会因一次延迟尖峰
误判。

### 判定分级（需求 7）

每条结论带可解释的严重程度：

`info` < `warning` < `minor` < `major` < `critical`

- `warning`：边界情形，标记但不拒绝（如单次超速尖峰）。
- `minor` 及以上：默认拒绝（`RejectThreshold` 可配置）。
- 复核时边界情形被明确归类（`Borderline`）并给出依据。

### 拒绝原因（需求 4）

所有异常输入都被拒绝并给出可互相区分的理由，**不会崩溃或静默丢弃**：

| 原因 | 触发条件 |
|------|----------|
| `duplicate` | 同一序号已提交 |
| `rollback` | 序号回退（迟到，低于前沿） |
| `seq_jump` | 序号跳跃超过 `MaxSeqGap` |
| `forged_time` | 时钟偏移/未来时间/非单调/散度异常 |
| `tampered` | MAC 校验失败（篡改或伪造） |
| `queue_full` | 等待队列或在途操作超限 |
| `invalid` | 结构非法（空字段、序号 0、未知类型、负伤害） |
| `cheat` | 违反游戏规则（速度、攻击频率、资源、伤害） |

## 可追溯与重放（需求 3）

每条判定记录（`Verdict`）包含：

- `VerdictID`：唯一判定编号。
- `MatchID` / `PlayerID` / `Seq`：追溯到具体操作。
- `Kind`：`accepted` 或 `rejected`。
- `Reasons`：拒绝原因列表。
- `Findings`：触发的规则、观测值、允许范围、严重程度、依据。
- `RuleVersion`：判定时绑定的规则版本。
- `StateVersion`：判定后的已提交状态版本。
- `DecidedAt`：服务器时间。

**重放确定性**：引擎记录每个操作的（操作内容、服务器接收时间、边界拒绝原因）。
重放时按到达顺序通过同一确定性路径重新评估，结论与在线判定**逐条一致**
（`replay.Equal` 比较判定 ID、类型、规则版本、状态版本、原因、规则发现）。

## 多玩家并发（需求 5）

- 每个对局一个 goroutine，**单玩家慢或恶意高频不影响其他玩家**（不同对局独立）。
- 提交操作永不阻塞其他对局：等待队列满时立即返回 `queue_full` 判定。
- 上界均可配置：`InboxCapacity`（等待队列）、`MaxPendingPerPlayer`（在途操作）、
  `VerdictStoreCapacity`（判定记录）、`ReplayLogCapacity`（重放记录）。
- 任意时刻 `Snapshot()` 返回单个已提交版本的状态与判定副本（持锁拷贝）。

## 规则版本化（需求 6）

- 每个对局在开始时绑定**当时生效**的规则版本（`MatchState.RuleVersion`）。
- 规则升级（`Registry.SetCurrent`）后：
  - 正在进行的对局仍使用绑定版本，结论不被改写；
  - 新对局使用新版本；
  - 已结束对局的历史判定仍带原版本号，可按版本追溯查询。
- 重放时使用记录的版本（`Log.RuleVersion`），而非当前版本。

## 申诉复核（需求 7）

`review.Review` 在状态副本上对原始操作重新评估：

- 返回是否维持（`Upheld`）、是否边界（`Borderline`）、复核严重程度与依据。
- **不改写**原始判定记录与权威状态。
- 证据不足（状态缺失、玩家不存在）时给出明确结论而非静默通过。

## 配置项

所有配置项见 `internal/config/config.go`，可通过 JSON 文件加载（`config.Load`）。

### 上界

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `InboxCapacity` | 256 | 每对局等待队列容量 |
| `MaxPendingPerPlayer` | 64 | 每玩家在途乱序操作上限 |
| `MaxSeqGap` | 128 | 允许的最大序号跳跃 |
| `DedupWindowSize` | 256 | 去重窗口（最近已应用序号） |
| `VerdictStoreCapacity` | 4096 | 判定记录上限（超出淘汰最旧） |
| `ReplayLogCapacity` | 8192 | 重放记录上限 |

### 容差

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `MaxSpeed` | 10.0 m/s | 权威速度上限 |
| `SpeedTolerance` | 0.20 | 抖动带（上限的 20%） |
| `SpeedWarnRatio` | 1.3 | 警告级超速比 |
| `SpeedMinorRatio` | 1.6 | 次要级超速比 |
| `SpeedMajorRatio` | 2.0 | 严重级超速比 |
| `MaxTeleportDistance` | 100.0 m | 单次位移上限 |
| `MaxAttackRate` | 4.0/s | 持续攻击频率 |
| `AttackBurst` | 6 | 突发容量 |
| `MaxDamage` | 50.0 | 单次伤害上限 |
| `ResourceMax` | 100.0 | 资源上限 |
| `ResourceRegen` | 5.0/s | 资源回复 |
| `AttackCost` | 10.0 | 每次攻击资源消耗 |
| `PlayerMaxHealth` | 100.0 | 生命值上限 |

### 时间

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `TimeSkewAllowanceMS` | 5000 | 时钟偏移允许（毫秒） |
| `FutureAllowanceMS` | 1000 | 未来时间允许（毫秒） |
| `TimeDivergenceFactor` | 2.0 | 客户端/服务器时间散度倍数 |
| `DivergenceMinServerMS` | 1000 | 评估散度的最小服务器间隔 |

### 策略与安全

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `RejectThreshold` | `minor` | 达到该严重程度的判定拒绝操作 |
| `MACKey` | （内置） | HMAC 签名密钥（进程内共享） |

## 测试

```bash
go test ./...          # 全部测试
go test -race ./...    # 数据竞争检测
```

覆盖场景：

- **乱序**：操作按 1,3,2,4 到达，最终按 1,2,3,4 应用。
- **重复**：同一序号提交两次，只应用一次。
- **迟到/回退**：去重窗口外的旧序号被拒绝为 `rollback`。
- **序号跳跃**：超过 `MaxSeqGap` 被拒绝。
- **伪造输入**：篡改 MAC、伪造时间、结构非法均被拒绝且理由可区分。
- **并发**：多玩家并发提交无崩溃、无静默丢弃；慢玩家不阻塞他人。
- **规则版本切换**：新对局绑定新版本，旧对局结论不被改写。
- **网络抖动不误判**：抖动管道（20ms 延迟 + 15ms 抖动）下正常操作全部通过。
- **重放确定性**：重放结论与在线判定逐条一致。
- **申诉复核**：维持作弊判定、边界情形归类、不改写原判定。
